# 端末内の診断を確かめ、手動で共有する

1. 任意のサンプルを開き、調べたい操作を再現する。
2. 「診断」を開く。操作の結果と最新日の計測値を確認する。画面を下に引くと更新できる。
3. 「診断を書き出す」で JSON を作り、「共有する」からファイルや Google Drive を選ぶ。Drive は iPhone にインストールして利用者自身で設定する。共有を止めるときはシステムの共有画面を閉じる。
4. 調査時は診断と別に、再現手順、期待した動作、発生時刻と通信条件を伝える。

## データ形式

スキーマは JSON v1。生成日時、直近 30 × 24 時間の開始日時、保持日数、書き出し時のバージョン・ビルド・ソースリビジョン、OS と端末種別を含む。端末種別は機種識別子で、シリアル番号やユーザー設定の端末名は使わない。アプリ更新をまたぐファイルの `app` は書き出し時のビルド。ビルドごとの比較には更新の前後に別々のファイルを書き出す。

日付は UTC の ISO 8601。集計は UTC 日を単位に、サンプル、操作種別、結果ごとに件数を分ける。計測付の操作には計測件数、時間の合計、最大値が入る。平均は合計を計測件数で割る。直近の操作は日ごとに最大 40 件。AR のフレーム間隔は集計のみ。エラーは型付きの結果で記録し、生のエラー文字列は取り込まない。ユーザーの入力、URL、座標、検索語、画像、認証情報は診断 API に渡さない。

## 保持、容量、性能

`DiagnosticStore` actor が型付きイベントを受け取り、2 秒間にまとめてアプリ専用領域へ書く。ファイルは UTC 日単位。起動、復帰、書き出し、書き込み時に期限を確認し、最古の日は期限を過ぎた操作だけを削除する。アプリが停止中は削除処理を実行できないため、次回に期限切れを除く。ファイルはバックアップ対象から外し、保護された原子的な書き込みを使う。書き込み前の強制終了では直近の未保存分が失われる場合がある。

1 UTC 日の枠は操作 384 件、AR フレーム間隔 640 件。枠を満たすと同日の超過イベントを数値集計にも加えず、`recordingLimitReached` を表示する。古い日を容量確保のために先に消す処理は持たない。物理上限は日あたり 256 KiB、最古の部分日を含む最大 31 ファイルで約 7.75 MiB。原子的な置き換え中は一時ファイルの分を要する。過負荷の確認には同じ操作の連打と 10 分の AR 利用を行う。

容量不足などで書き込めないときは診断画面に表示し、メモリの同じ枠に保持して次の書き込みで再試行する。容量の回復前に終了すると未保存分は失われる。書き出しは一時領域に保護付きで保存し、過去の一時コピーは次回書き出し時に整理する。共有後のコピーは保存先で利用者が扱う。

## Apple の診断との関係

| 取得先 | 得られるものと制約 |
| --- | --- |
| TestFlight と App Store Connect のクラッシュ・フィードバック | Apple に届いたビルド別クラッシュやテスターのフィードバック。利用条件と集計遅延があり、すべての操作は含まれない。解析時は同じビルドの dSYM を使用する。 |
| iPhone の設定 → プライバシーとセキュリティ → 解析と改善 → 解析データ | 端末にある OS の診断。利用者が対象ファイルを選べる。ファイル名、内容、共有の有無は OS 設定に依存する。 |
| MetricKit | `MXMetricManager` 購読をアプリに実装した場合に、OS が集約したメトリクスや診断ペイロードを受け取る。配信のタイミングや対象イベントは OS が決める。このアプリは購読していない。 |
| Instrumentation | Instruments の Allocations、Time Profiler、Energy Log、Xcode Organizer などで同一ビルドと条件を記録する。HLS の瞬間的な待機や AR の継続負荷は実機で確認する。 |

これらは別の取得経路。アプリの JSON に Apple のクラッシュや MetricKit のデータが自動で入ることはない。参照情報の確認日は 2026-11-28、対象は iOS 27 / Xcode 27。
